# 会话热路径：实现与验证记录

更新：2026-10-22 UTC。

本记录对应第一轮工作区重设计合入后的进一步优化：前端减少日期格式器创建、保留会话列表节点、局部切换会话并及时追平分页消息；后端批量读取限定数量的已授权会话，并缩短消息分页持有数据库锁的时间。前端诊断执行真实应用源码，使用合成接口和最小 DOM 适配器；后端诊断执行真实 Rust 函数，使用合成 SQLite 数据。**两组数字分别衡量本地代码路径，不代表生产 HTTP／网络、浏览器 DOM 解析、布局、绘制或真实用户输入延迟，也不能据此承诺“一帧完成”。**

第一轮固定每请求 200 ms 的串行请求对比保留在 [workspace-navigation-validation.md](workspace-navigation-validation.md)。那是不同基线、不同实验，不与本轮 CPU 数据合并。

## 1. 本次实现

### 前端

- **复用日期格式器。** 根据界面语言、时间显示类型缓存 `Intl.DateTimeFormat`；每次消息／列表更新检查系统时区，跨时区时清除格式器缓存。当前日期、过去日期、秒／毫秒时间戳、无值和非法日期保持原有语言与本地日期语义。
- **会话列表按稳定 ID 更新。** 比较上一次生成的结果，不读取浏览器序列化的 `innerHTML`。未变化的行保留全部节点；变化行保留外层链接和焦点，仅更新该行的内容；新增、删除、移动行使用对应节点操作，并恢复列表滚动位置。行输出缓存只属于当前已授权会话列表，不保存消息历史。
- **同一会话的列表／详情切换不新增导航请求。** 已挂载且可用的会话保留消息、草稿、滚动位置、列表和轮询控制器，只切换视图状态。既有后台轮询仍按自己的时间运行。“零请求”指这次视图切换自身不发出请求。
- **已知的不同会话只重建消息区域。** 标题可使用当前已显示列表中的元数据；消息区域先清除原会话内容，再发起新的、强制新鲜的历史读取。索引在后台更新，不阻塞这条历史请求。没有复用未经本次授权读取的旧消息历史。
- **不满足条件时走完整加载流程。** 包括 session 已过有效期、身份或语言改变、尚未准备好、存在错误／撤权状态、未知会话或其他路由。管理员的 `/admin` 仍进入总览，不能被消息快速路径截获。普通 `go()` 与浏览器前进／后退使用同一个受保护入口；显式刷新当前页仍重新读取。
- **增量消息连续追平。** `has_more` 且游标前进时连续读取后续页，页间让出任务；每轮最多 4 页，有剩余时使用 250 ms 的后续调度，正常空闲轮询为 5 秒。无进展游标不会造成循环。每次返回都核对当前身份、会话代次与撤权状态。
- **撤权后的迟到响应不能恢复内容。** 修复原有“更早消息”与发送成功回执的迟到竞态；撤权后清空内容与草稿、禁用发送，并中止所属读取。已经提交的写操作不因切页被取消，也不会自动重发。
- **主动离开会话不报读取失败。** 离开会话时取消“更早消息”读取，取消结果不会传到全局错误提示；真实的当前会话读取失败仍保留原有错误处理。

主实现位于 [service-ui.js](../static/service-ui.js)，导航接入仅修改 [app.js](../static/app.js) 的 `go()`／`render()` 入口。通用节点匹配的线性处理另见 [navigation.js](../static/navigation.js) 及其身份保留测试；下方 CPU 实验不执行该 DOM 匹配器，因此没有把它的收益计入数字。

### 后端

实现位于 [chat.rs](../src/chat.rs)。会话索引不再在 Rust 中对每个返回会话重复调用单会话元数据函数，而是批量取得参与者、最后消息、未读数和可写状态。授权、排序与 `recent_list_limit` 仍在服务端执行，单会话的独立授权入口保留。

最初的批量 SQL 候选没有充分约束消息元数据展开的范围，可能先为超出返回上限的会话计算最后消息与未读数。最终改为先用 `WITH recent AS MATERIALIZED` **物化已授权、已排序、已限量的会话 ID**，再为这组 ID 展开元数据；本记录中的后端数字只对应这一最终实现。未读数和最后消息仍有针对所选会话的 SQL 子查询，不能将“批量查询”理解为消除了全部逐会话数据库工作。

`ensure_matches` 使用一次带当前权限条件的 `INSERT … SELECT` 补齐尚不存在的会话，保留已有会话时间戳。消息分页则先在事务内授权并复制原始字段，提交事务、释放数据库互斥锁后，再执行 Markdown 解析与 HTML 清理；授权检查和清理仍然存在，只改变其执行位置。这项锁占用修改针对消息分页，下面的列表函数基准没有单独测量它的并发收益。

## 2. 测量结果

### 2.1 前端：五轮 CPU 对照

基线是第一轮重设计合入点 `f0c8127039396890092a615dca6ecb7fd0b0ad9e`，与 `cb339ef` 的静态源码相同。新版是整合上游 `ce0145d3a9a3fc59cca47ff0cf22205824f9707a` 后的工作树，包括本次热路径修改。上游主题／支付页面的变化保留，因此两版完整页面 HTML 不完全相同；这是会话路由生成诊断，不是框架对比。

最终报告 [chat-cpu.json](validation/chat-cpu.json) 已按包含“更早消息主动取消处理”的最终源码重新采样，时间为 `2026-10-21T23:58:55.183Z`。每种数据规模、每个版本先预热一次，再各测五次，交替版本顺序。每次使用新服务实例、预先确认的登录状态、20 或 200 个合成会话与当前会话的 100 条消息。两版均读取同样的会话索引和消息接口；请求延迟设置为 0 ms。定时器本身仍会产生调度延迟，因此主要比较最后一次所需会话读取结束到 HTML 提交的区间。

#### 仍存在的完整页面工作

本实验测的是从其他工作区页面首次打开会话，两版仍各提交两段完整页面 HTML（页面壳和内容）。20 个会话场景中，两次提交合计为 61,612 → 68,392 字节；200 个会话场景为 153,715 → 167,615 字节。新增行 ID 与上游主题改动增加了 HTML，**本轮没有宣称完整页面字符串生成、解析或提交次数已经消除**。

同一会话的视图切换与稳定行更新由行为测试验证；未在这个 CPU 表里测量其 DOM 修改耗时。完整浏览器还需要独立观察字符串解析、节点变动、样式与布局、绘制、长任务和真实交互响应。

### 2.2 后端：实际 Rust `list_conversations` 对照

基线取自同一个 `f0c8127039396890092a615dca6ecb7fd0b0ad9e` 的 `src/chat.rs`；新版使用最终物化限量 ID 的实现。临时诊断二进制包含生产 `src/lib.rs` 和原样保存的基线聊天模块，两者运行在同一个 `AppState`、相同依赖和同一个预置的内存 SQLite 数据库中。数据库包含 2,000 个平台会话，每个 50 条消息，共 100,000 条；以管理员读取，读标记位于各会话第 25 条消息，部分参与者含头像、消息含 Unicode，更新时间含并列值。数据生成与房间创建不计时。

每个返回上限、每个版本预热 8 次，然后测量 61 对调用，交替基线／新版的先后次序。计时覆盖整个公开 `list_conversations` 调用，包括数据库互斥锁获取、IMMEDIATE 事务、授权、`ensure_matches`、SQL 准备与执行、返回 JSON Value 构造和提交。完整 JSON 相等检查、返回值析构、JSON 传输序列化、HTTP 与网络不计时。首次结果和全部 122 对测量结果都完成了完整 JSON 相等检查。方法与结果见 [chat-list-diagnostic.json](validation/chat-list-diagnostic.json)，控制台输出见 [chat-list-diagnostic-output.txt](validation/chat-list-diagnostic-output.txt)。

| 返回会话上限 | 基线中位数 | 新版中位数 | 基线样本 P10—P90 | 新版样本 P10—P90 | 本实验中位数减少 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 20 | 5.789830 ms | 4.318653 ms | 5.457542–6.636932 ms | 4.065292–4.712214 ms | 25.41% |
| 200 | 33.464820 ms | 16.134868 ms | 32.034474–36.487828 ms | 15.213125–18.472256 ms | 51.79% |

构建使用 `rustc 1.99.1 (58cf8f9c3 2026-10-13)` 直接链接，`opt-level=0`、`debuginfo=0`，只读复用已有 debug 依赖产物；实际链接 SQLite 3.50.2。编译与运行退出码均为 0。表中的 P10、中位数与 P90 分别为 61 个已排序样本的下标 6、30、54，并非生产分位数。

**这组结果属于预热后的本地、非优化构建、无并发负载、内存数据库、管理员读取平台会话的合成场景。** 它不覆盖冷库、磁盘 I/O、并发锁竞争、所有匹配会话／成员读取场景、生产 HTTP／网络或浏览器响应，也不能与前端 CPU 减少比例相加。两种返回上限下测得的本地中位数均降低，不能外推为线上容量或延迟保证。

**原始逐次耗时向量没有保存。** 原诊断进程仅输出了 P10／中位数／P90；逐次样本留在已结束进程内，JSON 的 `raw_samples_ms` 明确为 `null`。没有恢复或编造这些样本，也没有为补齐记录额外重跑。本记录保留了实际诊断源码、聚合结果和输出，因此可按相同方法重新运行，但无法从现有产物重算当次每个样本的分布。

## 3. 回归范围

### 前端

最终源码执行 `node --test tests/*.test.mjs`，12 个 JavaScript 测试文件全部通过，0 失败；`git diff HEAD --check` 也通过。[service-ui.test.mjs](../tests/service-ui.test.mjs) 包含 90 项测试，其中本轮新增 11 项针对性回归：

1. 日期格式器在中英语言、当日／历史日期、秒／毫秒、无值／非法值下保持原语义，复用时不反复构造。
2. 未变化轮询不读取已有 DOM 的序列化 HTML，也不重复重建列表。
3. 行移动、内容变化、新增与删除保留稳定行节点、焦点和滚动；未变化行的子节点不变。
4. 同会话列表／详情切换不发出请求，并保留消息节点、草稿和滚动；管理员总览等路由不会被误判。
5. 切换不同会话时立即移除旧消息，等待新授权历史，并且不等待较慢索引完成。
6. 后台元数据拒绝后，迟到历史不能恢复内容。
7. 连续切换及账户变化时，旧会话响应不能替换新会话。
8. `has_more` 连续追平、四页上限与 250 ms／5 秒后续调度符合预期。
9. 实际 `go()` 和浏览器历史使用的 `render()` 入口接通快速路径；session 失效后重新校验。
10. 撤权后的迟到更早历史／发送成功回执不能恢复私有内容，也不能追加读标记写入或重新发送。
11. 离开会话时取消在途的更早历史读取，不把主动取消传播到全局错误提示。

最小 DOM 适配器只验证相应节点身份、属性和接口行为，不构成浏览器视觉验证。独立代码审查也重新执行了两种撤权竞态，确认读取中止而已经提交的发送不取消。第一轮的 401 清屏、session 失效、旧导航取消、支付状态不可信返回等回归仍包含在完整前端测试中。
